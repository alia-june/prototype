# Integration gate

An integration is a replaceable boundary, not an implicit part of the native system.

## Closed by default

Every new integration begins closed. Before activation, define and review:

1. intended outcome;
2. authoritative upstream source;
3. exact version or byte identity;
4. license and attribution boundary;
5. required files, services and credentials;
6. local or remote destination;
7. configuration and secret-handling rules;
8. input, output and receipt contracts;
9. failure and partial-failure behavior;
10. rollback, removal or replacement procedure;
11. bounded validation and acceptance criteria;
12. provenance retained for derived information;
13. features and claims that remain unsupported; and
14. explicit production approval for the defined scope.

## No automatic acquisition or activation

Repository instructions must not automatically download software or data, install dependencies, create accounts, grant permissions, launch daemons, alter system configuration, ingest a corpus, enable a GPU path, register an agent host or publish an artifact.

Preparation, configuration and activation are distinct states. A passing local check proves only the stated check; it does not prove upstream authority, semantic correctness, production readiness or independent attestation.

## Relative and replaceable

Objects, orders, structures, processes, grammar, syntax, theories and derived relations have meaning only in an explicit context and version. Replacing an integration creates a traceable successor or alternative. It does not destroy the prior identity, evidence, recipe or receipt.

## R-02 — Local transport boundary

The HTTP transport specification requires validation of a supplied Origin, recommends localhost binding and authentication, and describes a single MCP endpoint. [MCP Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)

Recommendation: one loopback service with an explicit startup-configured root, bearer token, allowed Host/Origin policy, strict schemas, and no per-request executable overrides. Document payloads are data. The service must not accept Python, shell commands, arbitrary converter arguments, or external scripts as transformation operations. A stdio adapter can be added if an approved host requires it; it should connect to the same owner process rather than introduce another database writer.

These controls address the actual execution/path issues in PROJECT_ASSESSMENT.md F-01, F-02, F-07, and F-15. They do not create an OS security boundary against a compromised account.

## R-03 — Ordering and reduction

Compiler canonicalization provides an applicable design principle: bounded rewrite rules, convergence, and correctness independent of optimization. MLIR documents those principles, including elimination of known identities. We are borrowing the reasoning model, not proposing an MLIR dependency. [MLIR operation canonicalization](https://mlir.llvm.org/docs/Canonicalization/)

MLIR's effect discussion distinguishes value-producing operations from operations with implicit observable behavior that need additional analysis before reordering or removal. [MLIR effects rationale](https://mlir.llvm.org/docs/Rationale/SideEffectsAndSpeculation/)

Project inference: each operation should declare targets, reads, writes, dependencies and observation boundaries. Start with exact duplicate elimination, same-scope assignment supersession, and return-to-base elimination. Preserve original requests and associate execution reductions with rule IDs and conditions. Preserve source order whenever independence is unproved. No general text rewrite, inverse inference, or aggressive cross-scope rewrite is justified initially.

Example: A -> B -> A -> C -> A on an identical effective-font scope can reduce to zero font work if no intermediate output is required and all relevant effects agree. A partial-scope change, inserted content, changed inheritance, or explicit intermediate rendering can prevent that reduction. Sequential and optimized execution must agree on observable results and validation outcomes.

## R-04 — Persistence and recovery

SQLite documents atomic database transactions and serialized writers. These fit a single local owner process holding small streams, transformation records, receipts and metadata together. [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html), [SQLite isolation](https://www.sqlite.org/isolation.html)

Recommendation: use one database for original bytes, logical stream manifests, materialized semantic snapshots, transformation metadata, and idempotency receipts. Keep small text payloads inside it initially so a committed stream and its receipt can share a transaction. Large rendered artifacts require a separate staged/ready protocol; a database transaction does not atomically commit arbitrary external files.

WAL research: WAL permits reader/writer overlap but requires same-host shared memory and introduces checkpoint/backup responsibilities. The current official page also records the WAL-reset bug and fixed/backported versions. [SQLite WAL](https://www.sqlite.org/wal.html)

Recommendation: begin with rollback-journal mode, a serialized writer, durable settings, and short transactions; enable WAL only if measurements warrant it and the actual embedded SQLite version is verified against fixes. Do not infer SQLite version from Python's version.

Backup must use a consistent SQLite backup path and a coordinated artifact manifest. The online backup API is documented for live databases. [SQLite backup API](https://www.sqlite.org/backup.html)

## R-05 — Rendering as a reusable capability

Playwright documents browser launch/reuse through BrowserType and page screenshots/PDF output. PDF generation uses print CSS unless configured otherwise. [Playwright BrowserType](https://playwright.dev/python/docs/api/class-browsertype), [Playwright Page](https://playwright.dev/python/docs/api/class-page)

Recommendation: generate HTML from the semantic snapshot using packaged rendering code, reuse a managed headless Chromium worker, and cache artifacts by content plus the complete rendering profile. Use isolated contexts, declared fonts and page settings, bounded jobs, and local allowlisted assets. A warm worker is a proposed reduction in repeated startup work; no speedup has been measured. Changed layout may still require a real render.

A browser preview represents the service's semantic output. It is not evidence of the pagination or appearance of an exported DOCX in Word. Any such claim requires rendering that exact DOCX using an appropriate renderer and reviewing it.

Windows alternative: DirectWrite supplies device-independent layout and can use hardware acceleration with Direct2D. [Microsoft DirectWrite](https://learn.microsoft.com/en-us/windows/win32/directwrite/direct-write-portal)

Recommendation: defer DirectWrite/native renderer integration. It introduces a platform-specific rendering path before the CPU transformation contract has been established.

## R-06 — Formats and source fidelity

CommonMark defines a specific Markdown grammar; the v0.1 regex converter should not be expanded by guessing syntax. Use an explicitly named dialect and parser. Pipe tables need a declared extension because they are outside core CommonMark. [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/)

Pandoc documents a reader/AST/writer architecture, conversion losses, style references and style-preserving DOCX options. It does not promise universal lossless conversions. [Pandoc manual](https://pandoc.org/MANUAL.html)

python-docx documents paragraphs, runs and formatting, providing an option for controlled native generation and inspection rather than proving Word layout fidelity. [python-docx text model](https://python-docx.readthedocs.io/en/latest/user/text.html)

Recommendation: keep raw imported bytes and import diagnostics, then map supported content into an explicit semantic model. Markdown is an interchange/source representation; effective font assignments require additional semantic style data. Recommend this extension to the generated Markdown-first design explicitly rather than implying Markdown alone preserves fonts. Use packaged native DOCX output for the initial supported subset; offer configured Pandoc as an optional later adapter. Both consume the same semantic snapshot and declare supported losses.

Parser selection: markdown-it-py documents token parsing and CommonMark-based presets with explicit table support options. Recommend a named CommonMark-plus-tables profile, disabling active HTML and automatic text alterations, then mapping tokens to stable semantic blocks. This choice is proposed, not installed or tested. [markdown-it-py usage](https://markdown-it-py.readthedocs.io/en/latest/using.html)

## R-07 — Strictness and text coordinates

Pydantic documents strict validation and warns that JSON input can still have type-specific allowances. [Pydantic strict mode](https://pydantic.dev/docs/validation/latest/concepts/strict_mode/)

Recommendation: explicit operation kinds, exact boolean/integer constraints, forbidden unknown fields, nonnegative bounds, server-owned schema/version identifiers, and schema tests against both dictionary and JSON paths. Type annotations alone are not the acceptance proof.

Unicode grapheme boundaries differ from individual code points. Unicode's segmentation annex defines default grapheme, word and sentence boundaries. [Unicode UAX #29](https://www.unicode.org/reports/tr29/)

Recommendation: initial operations address stable block IDs and complete text nodes; defer arbitrary character-range styling. When ranges are added, specify coordinate units, base revision and boundary policy, including emoji and combining characters. Preserve original bytes; canonical semantic serialization must not silently normalize Unicode.

## R-08 — CPU model and later GPU lowering

NVIDIA emphasizes minimizing host/device transfers and evaluating the whole pipeline. [CUDA best practices](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)

Recommendation: build a portable operation description and reference executor first. Later lower measured, worthwhile operations to a GPU backend; compare semantic results with the CPU reference and separately assess visual tolerance. GPU residency, language changes, and universal GPU execution are not initial requirements. No GPU, driver, VRAM capacity or acceleration benefit was verified here.
